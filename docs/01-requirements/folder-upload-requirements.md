# Requirements: Folder Upload

## Status

Draft. Phase 1 FE, mock-only. Generated by `atlas-sdd-generate-all` for the `folder-upload` slice.

## Context

The `knowledge-space` slice already ships a Documents tab that renders a static batch summary, a progress list, and a file tree, with non-functional `Upload Folder` / `Upload ZIP` buttons (`renderDocs()` in `frontend/public/atlas-prototype.html`). This slice makes those buttons drive an interactive **mock** upload flow: a user picks a folder or ZIP, sees a generated file inventory and file tree, creates a batch, and gets a mock processing report — all with mock data, no real file I/O, no parsing, no network.

This slice refines, and does not redefine, `docs/batch-processing-design.md` (Batch / File Item / File Status / Reports model), `docs/mvp-scope.md` (mock batch status and file tree), and `docs/markdown-standard.md` (trace/confidence/review metadata).

## Slice Boundary

- **This slice owns:** the upload trigger interaction, mock file-inventory generation, unsupported-file classification, file-tree construction from inventory, batch creation from an inventory, mock per-file status progression, batch summary/progress derived from a created batch, and the mock batch report.
- **`knowledge-space` owns:** the Documents-tab shell, space navigation, and the pre-existing static baseline batch. Where behavior overlaps, `folder-upload` supersedes the static Documents-tab batch rendering while preserving its visual parity.

## Goals

1. Let a user simulate uploading a project document folder or ZIP into a Knowledge Space.
2. Produce a reviewable file inventory and hierarchical file tree from the selection.
3. Create a batch with mock statuses and a mock processing report.
4. Preserve source trace, confidence, and review status on every generated file item and report entry.
5. Keep the entire flow mock-only and adapter-neutral, with future real ingestion documented but not implemented.

## In Scope

- Interactive `Upload Folder` and `Upload ZIP` affordances on the Documents tab.
- Mock file-inventory generation: per-file original relative path, file type, and mock size.
- Supported vs unsupported classification by file type, with unsupported files surfaced distinctly.
- Hierarchical file tree built from inventory paths.
- Batch creation from a confirmed inventory: upload time, owner, source package name, file count, per-file initial status.
- Mock per-file status progression across the allowed File Status set.
- Batch summary metrics and processing progress derived from the created batch.
- A mock batch report (inventory, unsupported, conversion failures, low-confidence, review-required).
- Empty / all-unsupported / cancelled selection states.
- Bilingual (EN/zh) copy and day/night theme parity for all new surfaces.

## Out Of Scope (Current Phase)

- Real folder/ZIP reading, decompression, or file upload.
- Real Office→PDF conversion, PDF→Markdown parsing, OCR, or asset extraction.
- Backend API, persistence, or job queue (no API guide in this slice).
- Converter/parser/storage adapter implementations (interfaces are documented only).
- Authentication, real ownership, or permission enforcement.
- Any external network call, new runtime dependency, real company document, credential, or private path.

## Assumptions

- A mock "selection" is represented by a seeded in-memory sample set (not a real file picker result); a real `<input type="file" webkitdirectory>` may be wired later but must degrade to mock data in Phase 1.
- Owner defaults to the current mock user/space owner; no real identity is introduced.
- Supported types follow `docs/markdown-standard.md` source types (pptx, docx, pdf, xlsx, images); everything else is `UNSUPPORTED`.

## Open Questions

- Should the mock file picker use the browser directory picker (visual only, still mock inventory) or a purely synthetic sample? Default: synthetic sample with an optional non-functional picker button. (Deferred to design; see traceability.)
- Should multiple batches per space be listable in this slice, or only the most-recently-created batch? Default: single active created batch replaces the baseline static batch for the demo. (Deferred.)
