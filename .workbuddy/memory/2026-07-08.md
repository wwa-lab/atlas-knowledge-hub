## Repo overview: atlas-knowledge-hub

Explored the repo at user request ("帮我看下这个repo"). Key findings:

- **Project**: Atlas Knowledge Hub — internal knowledge product that turns doc packages (PPTX/DOCX/PDF/images) into reviewable, traceable Wiki pages via converter/parser adapters, SME review, graph + Ask.
- **README is stale**: still says "MVP = static prototype". Reality: full **Spring Boot backend** (480 Java files, 23 controllers, 27 services, 41 repos, 19 Flyway migrations) + **Vue 3 SPA frontend** (Vite+TS). Past Phase 2 into Phase 3/4 of the roadmap.
- **Backend is real & broad**: spaces, files, batches, conversion/parser/storage/vector/model adapters, ingestion, wiki ingest, graph-from-wiki extraction, ask/RAG, review+publish, auth/RBAC, audit log, connector sync v0, worker retry+dead-letter, manual URL ingest, retrieval quality metrics.
- **Frontend is monolithic**: essentially a single 5332-line `App.vue` (plus api.ts, types.ts, atlasMock.ts). Not componentized — by PROJECT_RULES this is intentional until SDD slice accepted, but is a maintainability risk.
- **Tests**: backend 73 test classes; frontend 3 Vitest specs + Playwright E2E organized by phase + 3-layer acceptance (first-layer mock, second-layer full-stack Docker PG, third-layer provider-backed deepseek/github-models).
- **Process**: extremely SDD-heavy, bilingual EN+zh-CN; 49 task files, many traceability + SDD-completion reports under docs/00-context.
- Current branch: `develop-leo`; many `codex/*` feature branches.

## Assessment: core capability implemented? (verified in code)
- **Control plane / product workflow = genuinely implemented** (real Spring Boot services + PostgreSQL + 73 test classes): spaces, batches, files, upload, conversion/parser run orchestration, worker retry/dead-letter, review & publish, graph-from-wiki, Ask API + citations + answer-review governance, audit log, auth/RBAC, connector sync, retrieval quality metrics.
- **Document intelligence core = architected but INACTIVE by default (mock).** Real adapters exist and are well-built (output sanitization, path validation, confidence checks, timeout): `TrinityOfficeConverterAdapter` and `DocumentNormalizeParserAdapter` shell out via `RuntimeExecutor` but are gated by `@Value("${atlas.runtime.trinity-office.enabled:false}")` / `document-normalize.enabled:false`. Mock variants (`MockTrinityOfficeConverterAdapter` etc.) share the same adapter key, so default resolution yields mock output. So out-of-the-box the "knowledge" produced is synthetic unless real `atlas.runtime.*` binaries + flags are wired in. Same pattern for vector (PgVectorAdapter vs MockVectorAdapter) and model (ConfiguredModelAdapter vs MockModelAdapter).
- Frontend = prototype-grade (monolithic App.vue), functionally present but not componentized.
- Bottom line: the *product system* is substantially real; the *document→knowledge intelligence* is a dormant, config-gated boundary with a mock default. Not a fake repo, but not a working knowledge extractor out of the box either.
